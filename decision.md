## Phase 2, Microstep 2 — Text Chunking Strategy (2026-09-15)

**D-2026-09-15-01 — chunk_id scheme**
`chunk_id = f"{source_path}_{index}"` | SHA-256 content hash of (doc_id, index, text) | Human-readable IDs are trivially debuggable in logs, Qdrant payloads and error messages (`company/about.md_3` vs `a3f9c1b7e2d84f01`), and the spec called for it explicitly | Flip back to hashing the moment re-ingestion runs without a delete-by-doc_id guard, or if silent index corruption is ever observed in practice.

**D-2026-09-15-02 — start_char / end_char placement**
Stored inside `DocumentChunk.metadata` | First-class typed fields on the dataclass | Avoids widening the frozen Contract 1 field list that 14 tests and 3 deep-dive docs already reference; keeps the amendment additive | Flip to first-class fields as soon as retrieval or UI code reads offsets on a hot path, where a `KeyError` from a typo'd `metadata["strat_char"]` would be a production bug rather than a test failure.

**D-2026-09-15-03 — chunking strategy**
Semantic chunking (embedding-based boundary detection) | Recursive character splitting; fixed-size windows; markdown-header splitting | Cuts on actual meaning shifts rather than arbitrary character counts, giving chunks that are internally coherent and therefore embed more cleanly | Flip to recursive character splitting if ingestion latency becomes unacceptable, or if measured retrieval quality does not beat the recursive baseline enough to justify ~5-8k extra embedding calls per full run.

**D-2026-09-15-04 — embedding provider for boundary detection**
Ollama (`nomic-embed-text`, local) | Cohere API; sentence-transformers in-process | Free, offline, no API key, and already a running service in `docker-compose.yml` with `OLLAMA_URL` plumbed through `Settings` | Flip to Cohere if CPU inference time makes full-corpus chunking impractical and an API budget exists; flip to sentence-transformers if offline is required but Ollama's server dependency becomes a burden.

**D-2026-09-15-05 — chunker implementation**
`langchain_experimental.SemanticChunker` | Hand-rolling the ~60-line algorithm | Battle-tested implementation with four threshold methods already built; ships fastest | **Flip condition is already partially met** — the package emits `DeprecationWarning: langchain-experimental is being sunset and is no longer actively maintained`. Flip to a hand-rolled implementation at the first breaking upgrade, or before any production deployment.

**D-2026-09-15-06 — breakpoint threshold method**
`standard_deviation` (mean + 1.5σ) | `percentile`; absolute distance threshold | Cuts only where a distance is statistically unusual *for that document*, so a genuinely uniform document is not forced to split at invented boundaries | Flip to `percentile` if chunk-count variance across documents becomes unmanageable, since percentile guarantees a predictable number of cuts per document.

**D-2026-09-15-07 — undersized trailing chunks**
Merge backwards into the predecessor chunk | Keep as-is; drop below a min-size threshold | A 30-character fragment embeds to near-noise and pollutes retrieval with context-free hits, while dropping it would silently lose content (e.g. "Total contract value: $2.4M") | Flip to keeping them if a hard maximum chunk size ever becomes a real constraint, since merging deliberately breaks the size cap.

**D-2026-09-15-08 — chunk size as soft cap**
`target_chunk_chars=500` logged-but-not-enforced | Hard split at 500 chars | Semantic chunking derives boundaries from meaning; hard-splitting would override the exact signal the strategy exists to follow, reintroducing the mid-sentence cuts we chose semantic chunking to avoid | Flip to hard enforcement if a downstream embedding model has a strict token limit that oversized chunks actually exceed.

**D-2026-09-15-09 — overlap parameter**
Dropped entirely (not implemented) | Implementing ~15% overlap as originally chosen | Overlap is a sliding-window concept with no meaning in semantic chunking — boundaries are detected, not stepped, so there is no window to overlap | Flip if the strategy ever changes to recursive/fixed-size, where overlap becomes both meaningful and necessary.

**D-2026-09-15-10 — Ollama client library**
`langchain-ollama==1.1.0` | `langchain_community.embeddings.OllamaEmbeddings` | The community class is deprecated and `langchain-community` is itself being sunset; installing the standalone package added no conflicts and no version bumps | Flip only if `langchain-ollama` is itself deprecated in favour of another integration package.

**D-2026-09-15-11 — embedder injection**
Injected via constructor, typed as a `Protocol` | Constructing `OllamaEmbeddings` inside `Chunker` | Lets the test suite pass a deterministic fake, keeping CI fast and offline instead of depending on a live model server | Flip never; this is a straightforward dependency-inversion win with no real cost.

**D-2026-09-15-12 — git hygiene scope**
Forward-only untrack of `.venv` (new commit) | Amend Initial commit + force-push; local-only amend | The Initial commit is already published on GitHub, so rewriting history would require force-pushing over public `main` | Flip to a history rewrite if repository clone size becomes a genuine problem and the remote is confirmed to have no other consumers.

**D-2026-09-15-13 — clearing deliberate learning exercises**
Filled in all five CI TODOs and ran `ruff format` | Leaving them as hands-on exercises | CI was passing while asserting nothing, which is worse than no CI — a green check that verifies nothing actively misleads | Flip never; the exercises remain available in `docs/ci_deep_dive.md` without leaving the live pipeline hollow.

## Offset-drift fix (2026-09-15, same day, after P2-M2)

**D-2026-09-15-14 — recovering chunk character offsets**
Whitespace-tolerant regex search (`\s+` between the chunk's words) | (a) trusting `SemanticChunker`'s own `start_index`; (b) plain `str.find` | `start_index` drifts because the splitter rebuilds chunks with single spaces then advances its tracker by the REBUILT length; plain `str.find` fails too, because that same normalisation means the rebuilt chunk often is not verbatim present in the source — verified, it fell back to the broken estimate on the exact repro case | Flip to tracking positions during splitting ourselves if we ever replace `SemanticChunker` with a hand-rolled splitter, which would make offsets exact by construction rather than recovered after the fact.

**D-2026-09-15-15 — the correctness criterion for offsets**
Assert `source[start:end].split() == chunk.text.split()` | Assert byte-for-byte `source[start:end] == chunk.text` | Byte equality is impossible by construction: the slice retains the source's blank lines while the chunk text has single spaces. Word-level equality proves the span points at the right REGION, which is what a UI highlight actually needs | Flip to byte equality only if chunk text is ever reconstructed from the source slice itself rather than from re-joined sentences.

## Phase 2, Microstep 3 — Token Counting & Metadata Enrichment (2026-09-15)

**D-2026-09-15-16 — which tokenizer**
`tiktoken` `cl100k_base` | `nomic-embed-text`'s own tokenizer via Ollama; keeping the char÷4 heuristic | Industry-standard, well-documented, works without a model server, and gives a consistent ruler for comparing chunk sizes. **Known mismatch, accepted deliberately:** we embed with `nomic-embed-text`, which tokenizes differently — so these counts do NOT predict what the embedding model actually sees | Flip to the embedding model's own tokenizer the moment token counts are used to enforce a real context-window limit rather than to compare chunks to each other.

**D-2026-09-15-17 — behaviour when the encoding can't be fetched**
Fail loudly at construction time, plus pre-warm the cache in the Docker build | Silent fallback to the char÷4 heuristic; vendoring the `.tiktoken` file into the repo | A silent fallback would make `tokens_approx` mean two different things depending on network conditions, which is painful to debug; baking the cache into the image at build time means the container never needs network at runtime | Flip to vendoring the encoding file if builds must run air-gapped, where even build-time network is unavailable.

**D-2026-09-15-18 — both counts hold the same number**
`approx_token_count` AND `metadata["tokens_approx"]` both carry the tiktoken count | Field keeps char÷4 while metadata gets tiktoken; renaming the field | Two numbers that disagree would force every reader to know which to trust; measured on real corpus text the gap is real (heuristic 100 vs tiktoken 79, ~27% overestimate) | Flip to renaming `approx_token_count` if its now-inaccurate name ("approx" holding an exact value) starts causing confusion in code review.

**D-2026-09-15-19 — pure enrichment, not in-place mutation**
`enrich_with_token_counts` returns NEW chunks via `dataclasses.replace` and a fresh metadata dict | Mutating `chunk.metadata` in place | `DocumentChunk` is frozen specifically to prevent post-construction edits; mutating its dict works only by exploiting a gap in that guarantee, and would make enrichment invisible action-at-a-distance | Flip only if profiling shows the extra allocation matters at corpus sizes far beyond today's 76 documents.

**D-2026-09-15-20 — injectable TokenCounter**
`TokenCounter` Protocol with a fake in tests | Calling tiktoken directly inside the enrichment function | Keeps the test suite offline and instant; without it, "fail loudly" would make CI on a fresh GitHub runner depend on a network fetch, since the runner is not the Docker image the cache was baked into | Flip never; same dependency-inversion reasoning as `Embedder` in chunker.py.

## Phase 2, Microstep 4 — Ingestion Pipeline Script (2026-09-15)

**D-2026-09-15-21 — data layout**
Keep `data/<category>/` and point the pipeline at `data/` | Restructuring everything under `data/raw/` as the spec assumed | Zero file moves, no test churn, and it avoids a verified trap: files under `data/raw/` with `data_root=data/` make `infer_category` return `"raw"` for every single chunk, silently destroying the category dimension hybrid search filters on | Flip if a second processing stage genuinely needs its own sibling directory (`data/processed/`), at which point `data_root` must move to `data/raw/` in the same change.

**D-2026-09-15-22 — pipeline includes enrichment**
loader → chunker → **enrichment** | The spec's literal loader → chunker only | Without enrichment the saved chunks carry the char÷4 estimate, which would make the spec's own "token distribution" report describe numbers already measured as ~27% wrong | Flip only if enrichment becomes slow enough to want a separate opt-in pass.

**D-2026-09-15-23 — output format**
One JSON file per source document, named `company__about.md.json` | A single combined `chunks.json`; JSONL | One document's chunks can be inspected or regenerated in isolation, and a partial failure damages exactly one file | Flip to JSONL when the corpus outgrows comfortable per-file inspection or a streaming loader is needed.

**D-2026-09-15-24 — generated chunks are gitignored**
`data/chunks/` in `.gitignore` | Committing chunks so a fresh clone has them | Chunks are reproducible from `data/` + code; committing them adds an unreadable diff to every parameter experiment | Flip if a reviewer must see output without running Ollama, at which point commit a small curated sample rather than the whole set.

**D-2026-09-15-25 — re-run policy**
Always re-chunk every document, overwriting | Skip if output exists; skip if source older than output | Skipping is silently wrong the moment chunking parameters change — untouched files keep boundaries from the OLD config, mixing two strategies in one dataset with no marker saying which is which | Flip to timestamp+config-hash staleness checking when a full run (~4 min at 76 docs) becomes too slow to tolerate.

**D-2026-09-15-26 — failure policy**
Skip the failing document, record it in the report, continue | Abort the whole run; skip but exit non-zero | One unreadable file should not discard the embedding work already done for everything before it | **Flip condition is close:** the resulting dataset LOOKS complete, so if anything ever consumes `data/chunks/` without reading `documents_failed`, switch to exiting non-zero.

**D-2026-09-15-27 — quantile method for the token distribution**
`statistics.quantiles(..., method="inclusive")` | The default `method="exclusive"` | Exclusive extrapolates beyond the observed data: for two chunks of 6 and 10 tokens it reports p25=5 and p75=11, values impossible for that dataset. Inclusive describes the chunks that actually exist, which is what a report about them should do | Flip to exclusive only if the report is ever reinterpreted as estimating a wider population the corpus was sampled from.

**D-2026-09-15-28 — interface**
Importable `run_pipeline()` plus a `python -m` CLI | Either alone | The function is testable without subprocesses; the `__main__` block gives a real command for the README | Flip never; the cost is a dozen lines of argparse.

## Phase 3, Microstep 2 — Choose & Lock Embedding Model (2026-09-16)

**D-2026-09-16-19 — hard token cap in the chunker**
Re-split any chunk over `max_chunk_tokens` (1500, counted as chars/4 = 6000 chars) at sentence boundaries, words as a last resort, applied after merging | Re-tuning the breakpoint threshold only; truncating at embed time | Embedding every chunk showed 1/214 rejected ("input length exceeds the context length", 13,599 chars). Tuning guarantees nothing for future documents; truncation silently loses the tail. Verified after the fix: 0/223 rejected, largest 5,983 chars | Flip to counting with the embedding model's own tokenizer if a text type (code, tables) turns out to tokenize far denser than chars/4 assumes.

**D-2026-09-16-20 — single source of truth for the model**
Extend `Settings` in `src/core/config.py` (model, digest, dim, context, cap, prefixes, collection) and have chunker, pipeline and Qdrant setup read it | Creating `src/config.py` as the spec named; moving the existing module | The model name was hardcoded in three unconnected places (`chunker.py`, `pipeline.py`, `setup.py`'s `VECTOR_SIZE`); two config modules would recreate that problem | Flip never; deviating from the spec's filename is cheaper than a second config module.

**D-2026-09-16-21 — pin by digest and verify at startup**
Store the model digest and refuse to run if Ollama serves a different one (pipeline and Qdrant setup) | Model name only; digest recorded in docs without a check | `nomic-embed-text:latest` is a moving tag — a re-pull can swap the weights, and old document vectors silently stop matching new query vectors with no error | Flip to name-only only if the model is ever served from an immutable source that guarantees versioned weights.

**D-2026-09-16-22 — task prefixes on by default, configurable**

## Phase 3, Microstep 3 — Embedding Pipeline (2026-09-17)

**D-2026-09-17-04 — fixed batch size from config, default 16**

**D-2026-09-17-05 — fail fast on any batch error, naming its chunk_ids**
Raise `EmbeddingError` for server, HTTP or connection errors | Bisect and skip the bad chunk; retry with backoff | The hard cap means a 400 should be impossible, so one is a bug to stop for; skipping would build an incomplete index that looks complete. **D-2026-09-17-06 — validate count, dimension, finiteness and unit norm per batch**
All four checks, before any Embedding is built | Count and dimension only; no checks | Each failure would otherwise reach Qdrant as a plausible vector; misalignment is undetectable afterwards. Mutation-tested: removing any check fails a test | Flip the norm check off (make it configurable) if a model that does not normalise is ever adopted.

**D-2026-09-17-07 — the Embedder verifies the model and applies the prefix itself**
`verify_model` in the constructor, `as_document` inside `embed_batch` | Caller responsibility; split responsibility | A caller cannot forget either, and an Embedder instance existing proves the pin matched | Flip if the same class must also embed raw, unprefixed text for another model or task.

**D-2026-09-17-08 — embeddings stay in memory; M4 stores them**
`embed_batch` returns `list[Embedding]` | Disk cache keyed by chunk/text/digest; writing straight to Qdrant | Keeps the embed/store boundary visible and avoids a cache with its own invalidation rules; re-embedding costs ~200s | Flip to a cache when the corpus grows enough that re-embedding costs more than maintaining invalidation.

**D-2026-09-17-09 — rename the chunker's Protocol to `SentenceEmbedder`**
New class keeps the spec name `Embedder` | Different name for the new class; two classes named `Embedder` | The chunker's interface embeds sentences for boundary detection and knows nothing of prefixes or pinning; one name for two concepts invites wrong imports. **D-2026-09-17-10 — `read_chunks` loads every JSON in data/chunks except the report**

## Phase 4, Microstep 4 — Entity Deduplication and Linking (2026-09-21)

**D-2026-09-21-01 — build order: deduplication first, as a pure function, on a gold set from the corpus audit**

**D-2026-09-21-02 — "linking" means ingest-time only: merge within a batch, keep aliases, return a map**

**D-2026-09-21-03 — matching: per-label normalisation, then subset match only when exactly one candidate fits**

**D-2026-09-21-04 — a middle initial is a word, not noise**

**D-2026-09-21-13 — sequencing: the extractor is its own step, before the ingestion job**

## Phase 5, Microstep 1 — Graph-Based Retrieval (2026-09-23)

**D-2026-09-23-01 — entity linking: whole-word match against the graph's own current names**
`GraphRetriever._find_entities` (via the free function `_match_entities`) checks every name Neo4j currently holds for each of the 5 named labels against the query text, whole-word and case-insensitive, reusing `extractor.py`'s own `_mentions` regex shape | fuzzy/normalised matching, or NER/embedding-based linking | the corpus is a small, closed, enumerable vocabulary (111 real names as of this run: 33 Company, 32 Employee, 8 Product, 29 Contact, 9 Location); exact matching is deterministic, needs no new dependency, and is the same technique already proven correct by 62 extractor tests | flip to fuzzy or embedding-based linking if the retriever ever needs to work over open-ended, paraphrased questions rather than this fixed corpus's own vocabulary.

**D-2026-09-23-02 — chunk hydration: read_chunks() from disk, filtered to found ids**
`GraphRetriever.__init__` loads every chunk from `data/chunks/*.json` once and indexes it by `chunk_id`; `retrieve` looks the winning ids up in that dict | fetch chunk text from Qdrant by point id | the graph's own `Chunk` nodes hold no text by design (P4-M2); `read_chunks()` is the same P2 output every other stage (P3's vector ingestion, P4's graph ingestion) already trusts, so this retriever needs no new source of truth | flip if `data/chunks` and the live graph are ever allowed to drift out of sync without a joint re-ingest, at which point a single shared chunk store would be worth building.

**D-2026-09-23-03 — related chunks: MENTIONS union the entity's home-document chunks**
Two new `GraphStore` methods support this: `all_entity_names()` (every name, grouped by label) and `chunks_of_document(doc_id)` (every chunk_id via `HAS_CHUNK`); `GraphRetriever._chunk_ids_for` unions `MENTIONS`-derived chunk ids with, when a `DESCRIBED_IN` edge exists, every chunk of that entity's own document | `MENTIONS` alone | a document's own page can hold chunks that never repeat the entity's name (e.g. a contract's `## Terms` section, several chunks in, that never says "Carllm" again) -- verified live: `products/Carllm.md_2` (the product's own third chunk) is returned for "What does Carllm do?" precisely because of the home-document union, not a MENTIONS match | flip to MENTIONS-only if a home document's later chunks are ever found to be reliably irrelevant to questions about the entity itself.

**D-2026-09-23-04 — traversal: multi_hop_search(hops=2) per found entity, unioned across entities named in one query**
`GraphRetriever._entities_by_hop` calls `multi_hop_search` at each hop level 1..2 and diffs the two result sets to recover which entities are newly reached at hop 2 (since `multi_hop_search` itself returns nearest-first names, not a distance per name) | 1 hop only, or the full 3-hop cap | this is the step's stated core-learning goal (multi-hop traversal); hops=2 reaches an entity's contracts and the employees who work on it without the 3-hop risk of pulling in loosely-related chains; verified live: "Who works on Carllm?" surfaces `employees/Tyler Brooks.md_0` | flip to a larger or per-query-configurable hop count if 2 hops is ever shown to miss a genuinely relevant connection on this corpus.

**D-2026-09-23-05 — ranking: hop distance, then convergence count**
Chunks are sorted by `(minimum hop distance any seed reached them at, negative count of distinct seed entities that reached them)` | no explicit ranking, or a graph-centrality-weighted score | simple, deterministic, and directly verified: naming both "DriveSmart Insurance" and "Carllm" in one query promotes their shared contract chunk from 3rd place (found by "Carllm" alone) to 1st place (found by both), with no new scoring model | flip to a weighted/centrality score if hop distance and convergence count are ever shown to tie too often to be a useful ranking on a larger corpus.

> **Corrected 2026-09-24 (see D-2026-09-24-01 and D-2026-09-24-02).** The "3rd place to 1st" verification above was an insertion-order artifact, not evidence: the original code credited a seed for reaching a chunk at ANY distance, so overlapping neighbourhoods tied every shared chunk. The rule is now "count a seed only at a chunk's nearest distance", with `chunk_id` as a final tie-break so equal chunks no longer come out in a different order on every run.

**D-2026-09-23-06 — no entity found: return an empty list**
`retrieve` returns `[]` immediately, before any graph query, when `_find_entities` finds nothing | a fuzzy fallback match, or raising | verified live: "What is the weather today?" returns in 0.001s with an empty list, no query sent at all; graph retrieval is one signal meant to be fused with vector search later, and "no known entity" is an ordinary, expected outcome for many real questions, not a failure | flip once fusion with vector search exists and a documented fallback policy is designed for exactly this case.

**D-2026-09-23-07 — known names read from Neo4j once per GraphRetriever instance**
`store.all_entity_names()` runs once, in `__init__`, and its result is cached for the life of the instance | re-derive from `data/chunks` via `GraphExtractor.from_chunks` each call, or a hard-coded list | always reflects the graph's actual, deduplicated, canonical spellings -- the same source of truth `_chunks_for_entity`'s later graph queries use -- at the cost of one extra query (1.63s including driver warm-up, once) at construction | flip to a periodic refresh if a `GraphRetriever` instance is ever kept alive across a graph re-ingestion.

**D-2026-09-23-08 — module: new src/retrieval/graph_retriever.py, two additions to GraphStore's own API**
`GraphRetriever` wraps a `GraphStore`; `all_entity_names` and `chunks_of_document` were added to `GraphStore` itself, matching its existing public-method style, rather than raw Cypher living inside the retriever | a `retrieve()` method added directly onto `GraphStore` | keeps the same layering P3 already established (`QdrantVectorStore` vs. whatever composes "search" on top of it): a low-level graph primitive stays reusable by anyone, while entity linking, ranking and chunk hydration are retrieval POLICY, a different concern | flip if `GraphStore`'s public surface is ever found to need every retrieval-specific method folded in for some reason (none identified so far).

## Phase 5, Microstep 2 — Hybrid Retriever (2026-09-24)

**D-2026-09-24-01 — P5-M1 fix: ties in graph ranking end with `chunk_id`, never set-iteration order**
`GraphRetriever.retrieve` sorts on `(best_hop, -agreeing, chunk_id)`, with `chunk_id` newly added as the final key | leave ties in whatever order the `set` of chunk ids produced | `_chunk_ids_for` returns a `set`, whose string order changes with `PYTHONHASHSEED` on every process start, and `sorted()` is stable, so tied chunks came out in a different order on every run (found when P5-M2's sweep gave different fused lists for the same question; confirmed under `PYTHONHASHSEED=1/2/3`; the regression test fails under 4 seeds without the fix and passes under 4 with it). Disclosed side effect: alphabetical order ranks `company/` before `contracts/` before `employees/` before `products/`, so product pages sit last among ties | flip to a relevance-based tie-break (for example, chunks from the entity's own home document first) once there is evidence alphabetical order hurts real questions; Carllm at k=3 is the current example.

**D-2026-09-24-02 — P5-M1 fix: a seed counts toward agreement only at a chunk's NEAREST distance**
`retrieve` keeps, per chunk, each seed's smallest hop distance (`seed_hops`), then counts (`agreeing`) only the seeds whose distance equals the chunk's best | count a seed for reaching a chunk at any distance (the original rule in D-2026-09-23-05) | the original rule let seeds with overlapping neighbourhoods (a Company and the Product it licenses, two hops apart) give every shared chunk the same count, so agreement separated nothing and the alphabet decided; the "3rd to 1st" verification quoted in D-2026-09-23-05 was an insertion-order artifact. The new hermetic regression test failed before the fix. Treated as a bug against D-2026-09-23-05's stated intent, not a new design choice; reverting is one line | flip back to any-distance counting only if a case appears where an indirect reach should count as much as a direct one.

**D-2026-09-24-03 — fusion method: weighted Reciprocal Rank Fusion**
Each list adds `weight / (rrf_c + rank)` to every chunk it contains and the sums are sorted (`fuse_rankings`) | a weighted sum of normalised scores (min-max or relative-score fusion); vector-first concatenation | graph retrieval yields an ordering with no scores while vector search yields cosines, so only ranks are comparable across the two; RRF needs no normalisation, rewards a chunk found by both lists automatically, and is the published baseline (Cormack et al., SIGIR 2009) that Qdrant and Weaviate also offer | flip to score-based fusion if the graph retriever ever gets a meaningful numeric score, or if evaluation shows magnitude (a 0.95 versus a 0.60 cosine) carries information rank throws away.

**D-2026-09-24-04 — weights: non-negative multipliers, per call, constructor defaults 1.0/1.0**
`retrieve(query, k, vector_weight=None, graph_weight=None)`; `None` means the constructor default; only the ratio matters; negative, NaN, infinite, bool and both-zero values are rejected, and a zero silences one list's influence on order | fractions that must sum to 1; module-level constants | multipliers make `(1, 2)` and `(0.5, 1)` the same request, leave the caller no sum-to-one rule to break, and keep the spec's `retrieve(query, k, vector_weight, graph_weight)` call shape working | flip to normalised fractions if a config file or UI ever has to display "X% vector / Y% graph".

**D-2026-09-24-05 — smoothing constant: `rrf_c = 60`, configurable**
The constructor takes `rrf_c` (default 60) and `fuse_rankings` takes it as a keyword | c = 1 (top-heavy) or a value tuned on this corpus | 60 is the paper's constant and the one Weaviate documents; it flattens the curve (rank 20 is worth about 24% less than rank 1), which is why agreement between lists beats position inside one list; five questions are no basis for any other value | flip once a labelled set of 30+ questions exists to tune `c` against.

**D-2026-09-24-06 — candidate depth: each retriever asked for `3 * k`, fused list cut to `k`**
`candidate_multiplier` (default 3, configurable) | ask for exactly k; a fixed depth such as 50 or 100; unbounded | a chunk that is rank 9 in one list and rank 3 in the other can beat a chunk that is rank 1 in only one, but only if both lists are read deep enough to see it; depth = k would reduce fusion to re-ordering two top-k lists. Known, measured cost: results depend on k (`retrieve(q, 3)` is not `retrieve(q, 10)[:3]`: Carllm misses at k=3, hits at rank 3 at k=10), and no single depth wins both hard questions (depth ×10 fixes Carllm at every k but loses the CEO at k>=5) | flip to `max(3k, floor)` or a fixed depth if a caller needs prefix consistency (paging, prefix caching), or once an evaluation set can choose depth from data.

**D-2026-09-24-07 — failure handling: an empty graph list adds nothing; exceptions propagate**
A question naming no entity makes the result equal to vector order; an error from either retriever is not caught | catch graph errors and silently fall back to vector-only | "no known entity" is an ordinary outcome, but a broken Neo4j or Qdrant is a fault the caller must see; swallowing it would make the system quietly worse with nobody told | flip to an explicit fallback once a caller would rather have vector-only results than an error and there is somewhere (log or metric) to record the degradation.

**D-2026-09-24-08 — return type: `list[DocumentChunk]` from `retrieve`, `FusedChunk`s from `retrieve_with_scores`**
`FusedChunk` carries the chunk, the fused score, `vector_rank`, `graph_rank` and the raw cosine (`vector_score`) | `retrieve` returning scored objects; attaching scores to `DocumentChunk` | keeps the spec'd signature and P3's own convention (`search` versus `search_with_scores`), while the second method makes every position explainable; the live tests and the notes use it to show why a chunk ranked where it did | flip if every caller ends up needing scores, at which point `retrieve` becomes the odd wrapper.

**D-2026-09-24-09 — acceptance: the five pre-labelled questions, live; misses kept as strict xfail**
The five questions from `tests/test_retrieval.py` run against the real collection and graph; Carllm at k=3 is `xfail(strict=True)` with an honest reason plus a passing k=10 test; the sweep was used to describe sensitivity, not to choose the defaults | a new synthetic golden set; hermetic tests only; raising the default depth until Carllm passes | the questions were labelled before this retriever existed and include the two vector misses this step was meant to fix. Result: CEO "fixed" at k=3 (partly through the alphabetical tie-break, see D-2026-09-24-01; and the accepted chunk names the founder, not the CEO, so the label is lenient, found in P5-M3), Carllm not fixed at k=3 but fixed at k=10. Five questions can demonstrate an effect; they cannot tune weights, `c` or depth | flip once a labelled set of 30+ questions with a held-out part exists, which is the precondition for choosing any of those from data.

**D-2026-09-24-10 — execution: sequential, vector first then graph**
`retrieve_with_scores` calls `search_with_scores`, then `retrieve` | run the two concurrently (threads or async) | simplest, a deterministic call order, and easy to test with fakes; measured latency is the sum (vector median 85 ms + graph median 141 ms is about the hybrid's 230 ms) rather than the larger | flip to concurrent calls once that sum is shown to matter to a caller.

**D-2026-09-24-11 — module shape: new `src/retrieval/hybrid_retriever.py`, pure function plus Protocol-typed class**
`fuse_rankings` (no I/O) and `HybridRetriever(vector_store, graph_retriever)` taking anything that satisfies the two Protocols; no existing public interface changed | a subclass of `GraphRetriever`; a `hybrid` method on `QdrantVectorStore` | the arithmetic is tested with plain numbers and no services, the class with fakes that record their calls, and P3's and P5-M1's retrievers stay usable alone; a Protocol is not enforced at runtime, so an object with the right method names but different semantics would be accepted | flip to a shared base class only if a third retriever appears and duplicated validation starts to cost more than the coupling would.

## Phase 5, Microstep 3 — Reranker (2026-09-25)

**D-2026-09-25-01 — reranker: Cohere Rerank API**
`Reranker` sends the question and the candidate chunk texts to Cohere's hosted rerank endpoint through the already-pinned `cohere==7.0.8` SDK | local BGE cross-encoder (sentence-transformers); both behind one interface | the SDK is already a dependency and `cohere_api_key` is already a setting (Step 1.1 chose Cohere for reranking), so this is about 10 lines with no model download; a local BGE needs torch plus a 1.11-2.27 GB download, runs on CPU only on this machine (no CUDA GPU), and would have to live in an optional extra so CI (`pip install -e ".[dev]"`) does not install torch. **D-2026-09-25-02 — model: `rerank-v3.5`**
`DEFAULT_MODEL = "rerank-v3.5"`, a constructor argument | `rerank-v4.0-pro` (top quality) or `rerank-v4.0-fast` (low latency) | v3.5's 4096-token per-document context is documented, and no chunk in this corpus exceeds about 1,265 tokens (chars/4 estimate), so nothing is truncated or re-chunked by the service; the docs table does not state a context length for v4 | flip to `rerank-v4.0-pro` once an evaluation set can show the quality gain is worth its latency and cost.

**D-2026-09-25-03 — return type: `rerank` gives `list[DocumentChunk]`, `rerank_with_scores` gives `RerankedChunk`s**
`RerankedChunk(chunk, relevance_score, input_rank)`, a frozen dataclass | scores attached to the chunk; scored objects only | keeps the specified signature and the `search` / `search_with_scores` pattern of P3 and P5-M2; `DocumentChunk` is a frozen dataclass, so a score cannot be attached to it; `input_rank` records where the hybrid had put each chunk, so every move is explainable | flip if every caller ends up needing scores, at which point the plain method becomes the odd wrapper.

**D-2026-09-25-04 — candidate pool: chosen by the caller, not by the Reranker**
`rerank(query, chunks, k)` reorders whatever list it is handed; tests and the live report ask the hybrid for 20 candidates (`POOL_SIZE = 20`) and keep 3 | `Reranker` owning a retriever and fetching `multiplier * k` itself; a ready-made `RerankingRetriever` now | one job per class, and no repeat of P5-M2's "results depend on k" problem inside the reranker. Measured on the real corpus: the labelled answer is inside a 20-candidate pool for all five questions, but its position moves with N in a way nobody chose (CEO answer at hybrid rank 2, 3, 15, 21, 9 for N = 3, 10, 20, 30, 50), and the CEO label is lenient (the accepted chunk `company/about.md_0` says the company was founded by Avery Lancaster; the chunk stating the CEO title, `employees/Avery Lancaster.md_0`, is not in a 20-pool and enters only at N=50, rank 17) | flip to a composite retriever when the next step needs one call for "retrieve then rerank", and revisit N once an evaluation set exists.

**D-2026-09-25-05 — what the model reads: `chunk.text` only**
The `documents` sent are exactly the chunk texts, in input order, and nothing else (a test proves the title is not sent) | `title + text`; text truncated to a maximum length | it is exactly what the generator will later read, so the reranker judges the same words the answer will be built from; no truncation is needed with a 4096-token context | flip to `title + text` if entity questions keep missing chunks whose text never names their subject (a contract's later sections never say "Carllm"), which only an evaluation set can show.

**D-2026-09-25-06 — failure handling: errors propagate, and the SDK's hidden retries are switched off**
Nothing is caught. `build_cohere_client` passes `max_retries=0` and `timeout=30`, and a test through the real SDK on a stubbed transport proves a 429, a 500 and a 401 each cause exactly one request | fall back to the hybrid's order with a warning; retry with backoff | found by reading the SDK source: by default it silently retries 408/409/429/5xx twice with exponential backoff and waits up to 300 s, which would have made "propagate" untrue; consistent with D-2026-09-24-07 (nothing swallowed) | flip to retry-with-backoff (`max_retries=2`, one argument) if the trial key's 10 requests/min makes bursts common, or to a logged fallback once some caller would rather have unreranked results than an error.

**D-2026-09-25-07 — edge cases: empty input returns `[]` with no request; no relevance cut-off**
An empty candidate list returns `[]` without calling the API; `k` larger than the list returns everything reordered (`top_n = min(k, len)`); repeats of one `chunk_id` are scored once at their first position; `k` and the question are validated before any request; an out-of-range index in the response raises | an absolute or relative relevance threshold | thresholds depend on a model's score scale, which is not calibrated across questions, and one wrong value can drop the only correct chunk; the extra rules are the same defensive habits as P5-M2 (a repeated chunk must not take two places; a negative index would silently pick the wrong chunk) | flip to a threshold once an evaluation set shows how scores separate relevant from irrelevant chunks for this corpus.

**D-2026-09-25-08 — module shape: new `src/retrieval/reranker.py`, client injected, `from_settings` factory**
`Reranker(client, *, model)` takes anything with a `rerank(model=, query=, documents=, top_n=)` method (a Protocol); `build_cohere_client(api_key)` and `Reranker.from_settings()` build the real one from `.env` | `Reranker` constructing its own client; a backend interface with Cohere and BGE classes | mirrors `build_ollama_client`, `build_qdrant_client` and `build_driver`; tests use a fake client with no network, and a second layer runs the REAL SDK over `httpx.MockTransport`, built from the SDK's own response types so the request body and response shape cannot drift from the real API unnoticed | flip to a backend interface when a second reranker is added.

**D-2026-09-25-09 — acceptance: hermetic tests, a few live tests, and a before/after report on the five labelled questions**
35 hermetic tests (all 10 deliberate breakages of the code are caught); 5 live tests (one needs no Cohere key: every labelled answer is inside the 20-candidate pool), 5 Cohere calls per run paced 6.5 s apart under the trial limit; the "before" column is what the hybrid returns TODAY for `k=3`, printed next to the hybrid's own top 3 from the 20-pool, because those two differ | only hermetic tests; a labelled set of 20-30 questions with hit@k/MRR | the user chose the easiest acceptance option; five questions can show at most two movable cases, so the live report is a measurement to read, not a claim.
